# 站点经验库（一站点一份）

## 为什么按域名分

以前经验按「主题」散在 references 里（CDP 排障、真机联调…），查「这个站点有什么坑」要跳好几处。
现在**按域名建一份**：换链路先读它，跑通后回写它。同一个站点踩过的坑只踩一次。

## 命名

`references/site/<host>.md`，host 用完整域名，子域各算一份：

```
references/site/qianchuan.jinritemai.com.md
references/site/ads.example.com.md
references/site/report.example.com.md
```

公司内网域名（如有）也照这个规则，别另起一套。

## 什么时候读

开工前第一次接触这个站点：先 `ls references/site/`，有对应文件就先读，**再决定要不要重新探**。
已有结论（入口在哪、登录态多久过期、哪个弹窗会挡点击、导出按钮在不在视口内）能省掉一整轮录制。

## 什么时候写

某条链路在某个站点**真跑通之后**，回写 3–5 条（不是写论文）：

| 项 | 写什么 |
|---|---|
| 入口 | 从哪个页面点进去最稳（直链 / 菜单路径 / 必须从上级页点入） |
| 登录 | 登录方式（账密 / 扫码 / SSO）、登录态大约多久失效、有没有验证码 |
| 数据从哪来 | 已确认的接口（含关键参数）或「只能 UI」 |
| 坑 | 症状 → 根因 → 修复（一条一行，别写猜测） |
| 校验 | 这个站点什么算「数据真的拿到了」（行数？共N条？导出文件列数？） |

## 铁律

1. **只写验证过的**：没跑通的现象标「未验证」，不写成结论。
2. **不写账号密码**：账号打码，密码永不落盘（登录态存在 profile 目录里）。
3. **站点改版后先改这份文件**，再改脚本 —— 否则下条链路还会按旧经验走。
4. 一条经验写清「症状→根因→修复」，缺根因的就是没想明白，先别写。

模板：`references/site-_模板.md`（复制成 `site-<host>.md` 填内容）。
