# skill 写作纪律（writing-spec）

> 生成模式出包时与 create-playbook 九步并用；升级模式改 SKILL.md 前过一遍这里的 Pitfalls。总纲一句话：**文档跟版本走、动作前先探测、失败有剧本、高危必确认、长度做减法。**

## 五条核心原则

1. **文档指针化（discovery stub）**：skill 有可执行宿主（CLI/脚本/API）时，SKILL.md 只写触发词+环境探测+指针（给出「怎么向宿主要当前版操作细节」的命令），操作细节由宿主按已装版本实时供出；无宿主的 skill 才写全操作细节。防文档与版本漂移。
2. **先探测后行动**：正式动作前先拿环境快照（浏览器场景=先拿页面引用再操作；数据场景=先验证 API 可达再取数）。skill 须写明探测步骤。
3. **等待=轮询+验证**：异步/加载场景禁盲 sleep，用「轮询读状态→验证结果→再动作」；关键动作后必验证行为（改文案≠改机制，报 done 前看实现）。
4. **失败有剧本**：每个 skill 必备故障剧本节——常见失败模式+第一步恢复动作（如：会话坏了先关再重开；元素找不到先滚屏再重新快照）。
5. **高危动作须确认**：能力边界表加「高危动作」列——cookie 导出、云同步、公网暴露、账号变更、文件覆盖类动作，执行前须用户确认，不得混在普通流程里无标注。

## SKILL.md 标准结构（按序）

frontmatter（name / description 含触发词与排除区 / version）→ 环境探测 → 核心流程 → 能力边界表（含高危动作列）→ FAQ/故障剧本 → 自检清单。模板类 skill 另附 templates/。

## 长度纪律（防形式工程）

- 编号硬规则、阶段门控、evals.json等形式无实质的不学
- SKILL.md 不是越长越强，每节须能答「删了会坏什么」
- 反例黑名单好过空泛建议
- 质量标记类规范优先吸收外部已验证做法（如〔A/D/E〕数据质量分级）

## 升版与多副本同步

- 改 SKILL.md+模板 → 升版本号（语义化，只加不改）
- 维护多份副本（本机/备份/其他机器）的，改完同步全部副本并做哈希/字数校验，校验结果向用户报告

## Pitfalls

- 操作细节写死在 SKILL.md 里，宿主升级后文档 stale（应指针化）
- 高危动作混在普通流程里没有标出
- FAQ 写成形式工程（凑条数、无第一步恢复动作）
- 触发词太宽导致误触发（须写排除区，description 里说明不管什么）
- 升级只改了一份副本，多处失同步

## 自检清单（交付前）

□ description 含触发词与排除区 □ 有环境探测 □ 高危动作已标注 □ 有故障剧本 □ 每节通过「删了会坏什么」测试 □ 升版后各副本校验一致并报告
