# change-guard：改前拷问，改后验收

分级走：
- 零逻辑改动（错字、注释、纯文案）：直接改 + `node --check`
- 小改（不碰 state、存档、函数签名、依赖）：报一句范围就改 + `node --check`，免拷问和清单
- 其余一切改动：全流程走完，清单落盘 `变更.md`

## 改前
1. **验收清单**：改完在浏览器/实际环境怎么验证，2-5 条，给用户过目再动手；同时写进工作区根的 `变更.md`（格式见下——清单只在对话里，换个对话就丢）
2. **拷问**（一次问完，别挤牙膏）：
   - 牵连：哪些函数/界面会跟着坏？
   - 数据：老存档/老数据还认吗？
   - 同步：state 变了，UI 和存档哪要跟着动？
   - 回滚：大改先 zip 备份

## 变更单（落盘格式）

工作区根建 `变更.md`，一次改动追加一节在文件末尾（台账式，不每变开目录）。没走完全流程收工时，这文件就是下个对话续验的锚点：

```markdown
## <日期> <主题>
范围：<动哪个文件哪几个函数>
验收：
- [ ] <怎么验，每条给能直接跑的命令>
拷问：牵连… / 数据… / 同步… / 回滚<zip 名>
结果：<改完回填，每条贴命令输出摘要，勾掉对应项>
结论：全过 / 部分过（哪条没过、为什么）/ 没过
```

- 结论三档，**只有「全过」才算完**（对应 spec-kit 的 verified/partial/failed）
- 没验完就收工：结果栏写「待验：<哪几条>」，别留空白让人以为验过
- 跨对话续验：用户给了工作区路径后，读 `变更.md` 对应节，按没勾的清单接着跑——不靠对话记忆，也不许自己去翻没给过的路径

## 改中
只动清单内的，不顺手动别的。走偏念头冒出来按下表打住（借自 code-review skill 借口反驳表）：

| 念头 | 现实 |
|---|---|
| 顺手把这个也改了 | 不在清单内=记进变更单留给下一单，别混进这单 |
| 仓库太大，抽查几个文件就行 | 要么声明没扫的范围，要么分模块逐个来 |
| 两次结果不一致，挑个像对的 | 证据不足亲验再定，禁凭印象二选一 |

新写的代码：
- 禁静默降级：except:pass、吞错返默认值，必须打日志或带质量标记
- 假修先过三问：补判空——这值本来该是什么？加重试——操作能重复吗？吞异常——这个错归谁管？删校验/固定返回值/清缓存/加长延时=压症状，不是默认选项
- 新加抽象/封装过删除测试：删掉它用户能感觉到吗？感觉不到就别加

## 改后
- 清单逐条验 + state/UI/存档三处一致
- 证据配改动，「没报错」不算验过：文案/配置=打开文件核对；逻辑/脚本=真跑一次+边界值；页面/游戏=真开到目标页操作一遍
- 验证到哪层就写哪层：已改未运行／止于静态检查（node --check）／实际运行——前两层禁写成「验过」
- 新用的 API/配置项跑一遍，「看起来存在」不算（防幻觉）
- 全过才算完，「应该能跑/大概」=没验，禁当结论
- 回填里列问题时按 正确性>安全>可维护性>简单性>性能>优雅性 排序，风格/可维护性类不得顶掉正确性/安全类名额（档位隔离，防小噪音淹没真问题）；每条问题带一句白话影响（不修会感觉到什么）+ 建议档位（建议修/可缓/不必）——清单是给拍板的人看的
- 验完回填 `变更.md`：结果贴输出摘要、勾掉清单项、写三档结论——回填完这单才闭；没验到的范围在结论里点名（未验范围声明，别让人以为全覆盖），≤5 分钟能修的小问题单列 Quick wins 别混进验收项

## 修 bug
先复现 → 定位根因 → 才改；修完重跑清单，再用反例证伪一次（空值/空集合/极值/跨日），推翻不了才算修好。复现步骤和根因记进变更单（下次同病直接翻）。

- 验收撞上老 bug：先分清是这次引入的还是项目原有的，别让它背锅、也别拿它遮新问题
- 已改还失败：先确认跑的是新代码/新包（老包、旧缓存是惯犯）
- 偶发不再出现≠修好：收尾说清是根因修复还是暂时缓解
