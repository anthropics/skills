# Verification Orchestrator

현재 변경 사항을 수정하지 않고 검증한다. 구현 에이전트의 설명을 그대로 신뢰하지 말고 요구사항, 변경 파일, 실행 결과를 증거로 판단한다.

## 입력 확인

다음 내용을 먼저 확보한다.

- 원래 요구사항
- 완료 조건
- 허용 범위와 금지 범위
- 변경 파일 또는 비교할 diff

요구사항이나 완료 조건이 불명확하면 임의로 만들지 않는다. 해당 항목을 `REVIEW`로 표시하고 사용자 확인이 필요한 내용을 적는다.

저장소의 `AGENTS.md`, `CLAUDE.md`와 프로젝트 컨텍스트 문서를 먼저 읽고 그 지침을 따른다.

## 검증 그래프 실행

서로 다른 새 서브에이전트에 다음 스킬을 명시적으로 사용하도록 요청한다.

1. `requirements-review` 스킬: 요구사항과 완료 조건의 충족 여부
2. `code-review` 스킬: 기능 결함, 권한, 보안, 데이터 무결성, 회귀 위험
3. `test-runner` 스킬: 비용이 낮고 결정적인 검사부터 실행

각 검증 스킬은 Claude Code의 `Skill` 도구로 호출한다.

각 에이전트에는 같은 요구사항, 완료 조건, 허용 범위, 변경 대상을 전달한다. 구현 과정의 자기평가나 결론은 전달하지 않는다.

독립적으로 실행할 수 있는 검증은 병렬로 실행한다. 선행 결과가 필요한 검증만 순차 실행한다. Agent Teams는 사용자가 명시적으로 요구하지 않는 한 사용하지 않는다.

서브에이전트를 사용할 수 없으면 세 검증을 순서대로 실행하되 각 단계에서 이전 단계의 결론을 정답으로 간주하지 않는다.

## 결과 통합

모든 발견을 원인과 증거 기준으로 합친다.

- `ACTUAL`: 수정이 필요한 실제 결함
- `DUPLICATE`: 같은 원인의 중복 보고
- `FALSE_POSITIVE`: 요구사항이나 코드 증거로 반박된 보고
- `REVIEW`: 사용자 판단이나 추가 정보가 필요한 항목
- `DEFERRED`: 현재 허용 범위를 벗어난 항목

같은 원인의 발견은 하나로 합치고 어느 검증에서 발견했는지 기록한다. 증거가 없는 추측은 실제 결함으로 확정하지 않는다.

## 출력 형식

한국어로 다음 순서대로 보고한다.

1. 종합 판정: `PASS`, `FAIL`, `REVIEW` 중 하나
2. 실행한 검증 노드와 각 판정
3. 통합 발견 목록: 심각도, 분류, 원인, 증거, 영향, 권장 조치
4. 실행한 명령과 종료 코드
5. 실행하지 못한 검사와 이유
6. 사용자 확인이 필요한 항목

검증 중 코드를 수정하거나 커밋하지 않는다. 수정은 사용자가 검증 결과를 확인하고 별도로 요청한 뒤 진행한다.
