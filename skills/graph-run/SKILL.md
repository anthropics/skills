# Graph Run Lite

작업을 Markdown 기반 그래프로 실행한다. 별도 실행기 없이 에이전트가 그래프, 게이트, 계약과 상태를 기록한다.

## 원칙

- 완료 조건을 임의로 만들지 않는다. 없으면 사용자에게 질문한다.
- 각 게이트에서 멈추고 사용자 승인을 받는다.
- 확인한 값만 기록한다. 토큰 수와 비용은 추정하지 않는다.
- 검증 기준은 검증 스킬에 위임한다.
- 필수 완료 조건이 모두 검증되기 전에는 완료로 판정하지 않는다.
- 서브에이전트의 완료 여부를 짧은 간격으로 반복 조회하지 않는다. 결과가 모이는 지점에서 필요한 만큼 기다린다.

다음 작업에는 그래프를 사용하지 않는다고 보고하고 중단한다.

- 한 파일의 짧은 수정
- 완료 조건을 미리 쓸 수 없는 작업
- 모든 변경이 같은 파일에 몰리는 작업
- 운영 DB, 배포, 삭제가 필요한 작업

## 0단계 — 입력 확보

저장소의 `AGENTS.md`, `CLAUDE.md`, 프로젝트 컨텍스트 문서를 먼저 읽는다.

다음을 확보한다.

- 작업 목표
- 판정 가능한 완료 조건
- 허용 범위와 금지 범위
- 실행 가능한 검사 명령

검사 명령은 프로젝트 문서와 설정에서 확인한 것만 사용한다. 명령마다 정확한 명령, 실행 디렉터리, 런타임과 필요한 환경을 기록한다. 비밀값은 기록하지 않는다.

안전하고 비용이 낮은 범위에서 명령의 해석과 진입 여부를 smoke-run한다. 실행할 수 없으면 의존성을 자동 설치하지 않고 `UNVERIFIED`와 이유를 기록한다. 긴 E2E, 유료 API, 외부 시스템 변경 검사는 사전 실행에서 제외할 수 있다.

구현 전 변경 기준선을 만든다.

- Git 저장소: `status`와 diff
- 비 Git 프로젝트: 허용·금지 범위와 추적 대상의 경로·크기·mtime·해시

그래프, 승인 상태, 완료 조건과 검증 결과는 대화 안에서 간단히 관리한다. 별도 Markdown 실행 기록은 자동으로 만들지 않는다. 감사 기록, 장기 작업, 세션 간 재개가 필요하거나 사용자가 요청한 경우에만 작성한다.

### 게이트 0

완료 조건과 범위를 사용자가 승인할 때까지 다음 단계로 넘어가지 않는다.

## 1단계 — 그래프 설계

작업을 노드로 나누고 엣지를 정한다. 각 노드에 다음을 적는다.

- 할 일
- 입력
- 출력
- 판정 방법

병렬 배치 전에 확인한다.

- 선행 결과가 필요한 노드를 병렬에 두지 않았는가
- 두 노드가 같은 파일을 수정하지 않는가
- 조사, 계약, 구현, 테스트, 검증 노드를 구분했는가

의존성이 없는 노드만 병렬로 두고 결과가 합쳐지는 지점에서 기다린다. 사용자가 만든 그래프는 임의로 교체하지 않고 문제와 이유만 보고한다.

### 게이트 1

노드와 실행 순서를 사용자가 승인할 때까지 구현하지 않는다.

## 2단계 — 계약과 파일 소유권

병렬 노드가 공유하는 인터페이스가 있으면 구현 전에 계약을 파일로 고정한다.

계약에 필요한 항목:

- 이름과 의미
- 타입과 기본값
- 요청·호출 형태
- 성공 반환값
- 실패와 오류 조건
- 권한
- 값이 없을 때의 처리
- 유효성 검사

공유하는 산술 상한, 크기 의존 규칙, 상태 전이는 대표값과 경계값으로 검산한다.

파일 소유권을 확정한다.

| 노드 | 수정 가능 | 읽기만 | 수정 금지 |
| ---- | --------- | ------ | --------- |

### 게이트 2

계약과 소유권을 사용자가 승인할 때까지 구현하지 않는다.

## 승인 후 변경 통제

승인 뒤 요구사항, 노드, 엣지, 파일, 검증 방법, 계약이나 소유권의 실행 의미가 바뀌면 `CHANGE_CONTROL_REQUIRED`로 기록하고 영향받는 노드를 중지한다.

다음 영향을 기록한다.

- 완료 조건과 범위
- 그래프와 엣지
- 계약과 소유권
- 테스트와 검증 방법

완료 조건·범위·검증 방법 변경은 게이트 0, 노드·엣지 변경은 게이트 1, 계약·소유권 변경은 게이트 2에서 다시 승인받는다. 필요한 승인이 끝날 때까지 영향받는 노드를 재개하지 않는다. 영향받지 않은 완료 노드는 보존한다.

## 3단계 — 구현

각 구현 노드를 별도 서브에이전트에 맡긴다. 의존성이 없는 노드는 병렬 실행한다.

각 에이전트에 다음만 전달한다.

- 목표와 완료 조건
- 계약 파일 경로 또는 계약이 없는 이유
- 수정 가능·금지 범위

다른 구현 에이전트의 진행 상황이나 결론은 전달하지 않는다.

```text
계약 파일이 있으면 읽기만 한다.
계약 불일치를 발견하면 CHANGE_CONTROL_REQUIRED로 보고하고 멈춘다.
수정 금지 파일은 열어도 수정하지 않는다.
```

각 구현 웨이브 뒤 기준선과 비교해 변경을 분류한다.

- `AGENT_CHANGE`
- `TOOL_SIDE_EFFECT`
- `PRE_EXISTING`
- `UNKNOWN`

주체를 증명할 수 없는 소유권 밖 변경은 “위반 없음”으로 처리하지 않는다.

## 4단계 — 독립 검증

Claude Code의 `Skill` 도구로 `verification-orchestrator` 스킬을 호출하고 다음을 전달한다.

- 완료 조건과 금지 범위
- 변경 파일 또는 diff
- 계약 파일 또는 계약이 없는 이유

구현 에이전트의 자기평가와 결론은 전달하지 않는다.

완료 조건마다 검사 방법, 상태, 증거를 연결한다.

- `PASS`
- `FAIL`
- `BLOCKED`
- `NOT_RUN`

브라우저 검증은 완료 조건일 때만 사용한다. 자동 테스트를 먼저 실행하고 브라우저를 실행할 수 없으면 이유와 함께 `BLOCKED`로 기록한다.

## 5단계 — 분류와 수정

검증 결과를 원인과 증거 기준으로 분류한다.

- `ACTUAL`
- `DUPLICATE`
- `FALSE_POSITIVE`
- `REVIEW`
- `DEFERRED`

같은 원인은 한 건으로 합친다. `ACTUAL`만 해당 파일 소유자에게 수정하도록 맡긴다.

다음은 임의로 수정하지 않는다.

- 완료 조건에 없는 취향 판단
- 검증 결과가 충돌하는 항목
- 범위를 넓혀야 하는 항목
- DB, 배포, 삭제가 필요한 변경

### 게이트 5

`REVIEW`와 범위 밖 항목은 사용자가 방향을 정할 때까지 수정하지 않는다.

## 6단계 — 재검증

수정한 부분과 관련된 검증만 다시 실행한다. 새 결함이 나오면 분류 단계로 돌아간다. 같은 결함이 세 번 반복되면 멈추고 사용자 판단을 요청한다.

## 7단계 — 판정과 종료

전체 판정:

- 필수 완료 조건이 모두 `PASS`이고 독립 검증이 실행됐으면 `PASS`
- 실제 결함이 남으면 `FAIL`
- 사용자 판단이 필요하면 `REVIEW`
- `BLOCKED`, `NOT_RUN`, 미실행 독립 검증이 남으면 `INCOMPLETE`

사용자에게는 다음만 간단히 보고한다.

- 완료한 작업
- 주요 변경
- 검증 결과
- 미해결 사항
- 별도 기록이 있을 때만 그 경로

상세 기록을 최종 답변에 그대로 옮기지 않는다. 별도 사용자용 결과 문서가 없고 문서 자체가 작업 산출물도 아니라면 “작업 내용을 사용자가 읽기 쉬운 간단한 문서로 정리할까요?”라고 묻는다. 동의한 경우에만 작성한다.

커밋과 푸시는 사용자가 별도로 요청한 뒤 진행한다.
